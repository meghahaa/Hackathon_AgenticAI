# Discharge-Planning & Follow-up Copilot (BC-AAIE-HACK-12)

A LangGraph multi-agent copilot that builds a **draft** discharge plan from a synthetic record,
retrieves and cites the follow-up policy, flags readmission risk with the factors behind it, drafts
the follow-up schedule, and routes high-risk or order-change cases to a clinician. It is traced with
Arize Phoenix, cost/latency governed, guarded (input/output guardrails, audit trail, PHI masking),
documented (governance pack), and evaluated (DeepEval with Gemini as judge + agent tests).

**Model provider: Google Gemini** (`gemini-3.5-flash-lite` primary, `gemini-3.6-flash` automatic
fallback, `gemini-3.1-flash-lite` as the DeepEval judge). An opt-in Groq quota fallback exists but is off by default;
see [Configuration](#configuration). All data is synthetic. No Docker, no external DB: pip + Python.

## Quick start (local run runbook)

Linux / macOS:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.lock                  # exact versions (see below)
pip install --no-deps -r requirements-guard.txt   # LLM Guard (see below)
python -m spacy download en_core_web_sm           # Presidio NER model, 12.8 MB
cp .env.example .env                              # then put your GEMINI_API_KEY in .env
```

Windows (PowerShell):

```powershell
py -3.12 -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.lock                  # exact versions (see below)
pip install --no-deps -r requirements-guard.txt   # LLM Guard (see below)
python -m spacy download en_core_web_sm           # Presidio NER model, 12.8 MB
copy .env.example .env                            # then put your GEMINI_API_KEY in .env
```

`requirements.lock` pins every package of the working venv (Python 3.12). It is generated by
`python scripts/freeze_lock.py` (`pip freeze`, not hand-written), without `llm-guard` and the spaCy model, which are
installed by the two lines after it. Windows-only packages (`pywin32`, `colorama`) carry platform markers, so the
same lock installs on Linux/macOS. `requirements.txt` holds the loose version ranges;
`pip install -r requirements.txt` works too, but pip may then choose newer versions than the ones tested.
On Windows, if pip fails with "No such file or directory" under `torch\include\...`, the venv path is too long for
the 260-character limit: use a shorter project path or enable Windows long paths.

The spaCy model and LLM Guard are optional, and the copilot degrades without them. Without `en_core_web_sm`,
PHI masking uses the identifier registry and regex only, and guard results and audit records show `"ner": "unavailable"`.
Without LLM Guard, or if its model can't load, the injection check is regex-only and audit records show
`"injection_classifier": "unavailable"`. LLM Guard is installed with `--no-deps` because it pins
`transformers==4.51.3`, which conflicts with `sentence-transformers`. Its PromptInjection classifier
(`protectai/deberta-v3-base-prompt-injection-v2`, about 750 MB) downloads from Hugging Face on first use. To fetch
it ahead of time, run
`python -c "from llm_guard.input_scanners import PromptInjection; PromptInjection()"`.
Set `INJECTION_CLASSIFIER=off` to turn it off. Tests never load either model.

### Command 1: run the copilot (committed sample inputs)

The commands below are the same in bash (Linux/macOS) and Windows PowerShell, with the venv activated.

```bash
python scripts/run_cli.py --demo
```

Runs the 8 committed sessions in [`data/sample_inputs/demo_cases.json`](data/sample_inputs/demo_cases.json)
(multi-turn context, return-visit recall, prompt injection, cross-patient access, order-change
request, out-of-scope, ambiguous and unknown-patient cases). Phoenix starts automatically; open
<http://localhost:6006> while it runs. Other modes:

```bash
python scripts/run_cli.py --patient PT-1001 --message "Draft the discharge plan and follow-up schedule."
python scripts/run_cli.py --patient PT-1003 --session my-session --interactive   # reuse --session to continue
```

**Clinician sign-off (human-in-the-loop).** Every drafted discharge plan or follow-up schedule (any risk tier)
and every order-change request pauses at the `clinician_signoff` node (a LangGraph `interrupt`). Escalations,
refusals, clarifications, policy answers and risk-only answers do not pause. The CLI prints `status=AWAITING_CLINICIAN_SIGNOFF` with the draft. The paused session is
checkpointed in `state/checkpoints.sqlite`, so a clinician can sign off later in a new process:

```bash
python scripts/run_cli.py --patient PT-1003 --session copd-1 --message "Please assemble the discharge plan."
python scripts/run_cli.py --approve --session copd-1 --clinician "attending physician" --note "reviewed"
python scripts/run_cli.py --reject --session copd-1 --note "follow-up window too late"
python scripts/run_cli.py --request-changes --session copd-1 --note "add pulmonary rehab referral"
```

The result is `APPROVED_BY_CLINICIAN`,
`REJECTED_BY_CLINICIAN` or `CHANGES_REQUESTED`, plus an audit record (`actor=clinician, action=signoff`) in
`logs/agent_actions.jsonl`. A session with no pending draft refuses sign-off. See
[`docs/output-risk.md`](docs/output-risk.md#clinician-sign-off-a-real-pause-langgraph-interrupt).

### Command 2: regenerate the Phoenix traces, the evaluation and all evidence

```bash
python scripts/regenerate_evidence.py
```

One process: Phoenix preflight → synthetic data → reset logs/state → Phoenix → demo sessions → red-team attack set →
golden-set evaluation (DeepEval, Gemini judge) → span export + golden signals + dashboard → failure mining →
PII redaction demo + PHI/secrets scan → pytest. It takes about an hour at the default `GEMINI_RPM=10` request budget
and needs `GEMINI_API_KEY`. The committed evidence comes from this full run.

**Fast path for reviewers:**

```bash
python scripts/regenerate_evidence.py --quick
```

Same steps and output files, on a subset: demo sessions S1–S3 (6 of 14 turns: multi-turn, return-visit recall,
heart failure), one red-team attack per category (8 of 21) and golden cases G01–G12 (12 of 32, every intent,
including refusal, escalation and clarification). The committed evidence is not touched. Every output goes under
`state/quick_run/` (git-ignored): `logs/`, `traces/`, `reports/` (with `cli_run_results.json`, `redteam_results.json`,
`eval_report.json`, `golden_signals.json`, dashboards, `phi_secret_scan.json`, `pytest_report.txt`, ...) and the
session/memory SQLite files. Spans go to the Phoenix projects `<PHOENIX_PROJECT_NAME>-quick` and `-quick-eval`, so

flags: `--skip-eval`, `--skip-tests`, `--keep-state`, `--keep-phoenix-history`.

**Reading the hallucination rate.** The headline figure is `hallucination_rate_answers`, with the overall
`hallucination_rate` next to it (both in `eval_report.json` `summary`). DeepEval's HallucinationMetric (4.x)
scores the share of context items the output agrees with, so higher is better. A case counts as hallucinated
when its score is below the threshold. Refusals, escalations and clarifications are scored too, but they mostly
don't engage with the record context. So a non-answer **can** score 0.0 without inventing anything, because the
judge counts "did not address the context" as disagreement. In this run **3 of 7 non-answers scored 0.0** (G10,
G12, G23; `hallucination_rate_non_answers` 0.4286). The other 4 scored 1.0. Their faithfulness was 1.0 in all 7
cases, and the judge's reasons for the three zeros cite a refusal or a scope decision, not an invented fact. That
is why the overall rate is not the headline.

### Intents the supervisor routes

| Intent | Workers | Ends at |
|---|---|---|
| `full_discharge_plan`, `followup_schedule` | risk → policy → plan | `human_approval_gate` |
| `risk_assessment` | risk | `human_approval_gate` |
| `policy_question` | policy (answer with citations) | `output_guard` |
| `clinical_order_change` | none (never actioned) | `human_approval_gate` (always held) |
| `recall_prior` | none (long-term memory) | `output_guard` |
| `ambiguous` / `out_of_scope` | none | `clarify` / `escalate` |

### Safety properties (and the test that proves each)

* Clinical orders are copied by code, fingerprinted and verified; never generated by the LLM
  (`verify_orders_unchanged`, `tests/test_routing.py::test_high_risk_case_routed_to_clinician`).
* HIGH risk, order-change requests, quarantined injections and degraded generations are held for
  clinician approval (`human_approval_gate`). Every drafted plan / schedule and order-change request then
  pauses at `clinician_signoff` (LangGraph `interrupt`) and reaches `APPROVED_BY_CLINICIAN` only through a
  clinician resume (`tests/test_hitl.py::test_status_never_approved_without_resume`,
  `tests/test_hitl.py::test_exactly_draft_and_order_change_turns_pause`).
* Injection and cross-patient requests are refused before reaching the supervisor
  (`tests/test_routing.py::test_cross_patient_request_blocked_before_supervisor`); tool calls are
  scope-locked to the active patient (`tests/test_tool_contracts.py::test_logging_middleware_blocks_out_of_scope_patient_and_logs_it`).
* Patient identifiers never appear in logs or traces: HMAC pseudonyms (`pref_…`) + registry/regex
  masking + a PHI-masking span exporter.
* Runaway loops stop at `MAX_AGENT_STEPS` (soft guard) and LangGraph `recursion_limit` (hard backstop)
  (`tests/test_loops.py`).

## Configuration

All configuration is via environment variables (`.env`, git-ignored; template in `.env.example`).
Secrets are never committed. Key knobs: `GEMINI_MODEL`, `GEMINI_FALLBACK_MODEL`, `GEMINI_JUDGE_MODEL`,
`GEMINI_JUDGE_FALLBACK_MODEL` (optional; the judge never uses `GEMINI_MODEL`), `GEMINI_JUDGE_RPM` (own budget per
judge model), `GEMINI_RPM` (client-side request budget), `MAX_AGENT_STEPS`, `GEMINI_REQUEST_TIMEOUT_S` (deadline per Gemini
request; primary and fallback each get their own), `LLM_TIMEOUT_S` (backstop, keep it above), `TOOL_TIMEOUT_S`,
`PHI_HASH_SALT`, `GEMINI_PRICE_*_PER_MTOK` (for the cost estimate). Secrets rotation: see
[`docs/compliance.md`](docs/compliance.md#secrets-management).

**`PHI_HASH_SALT` is a demo value.** The committed evidence was generated with the salt from `.env.example`
(`change-me-local-dev-salt`). That is acceptable only because every patient is synthetic: anyone who has the salt can
recompute the `pref_...` pseudonyms. A real deployment must set its own secret `PHI_HASH_SALT` in `.env` and then
regenerate the evidence (`python scripts/regenerate_evidence.py`). Changing the salt changes every pseudonym, so the
committed evidence is not regenerated here.

**Model routing.** Each request goes to `GEMINI_MODEL` first. After a stall (`GEMINI_REQUEST_TIMEOUT_S`) or a 504,
the primary is sent once more. After that, or after any other error, the request goes to `GEMINI_FALLBACK_MODEL`.

**Groq quota fallback (off by default; a deviation from the brief's Gemini-only rule).** With
`QUOTA_FALLBACK_PROVIDER=groq` and `GROQ_API_KEY` set, a request goes to `GROQ_MODEL` (default
`openai/gpt-oss-120b`) only when the primary has failed (after its one retry, if it stalled) and the Gemini fallback
then returned 429 (quota), 503 (overloaded) or 404 (model unavailable). It is never used when the Gemini fallback
succeeds, never on a first stall alone, and never after a fallback timeout or any other error.
- **Judge:** the DeepEval judge uses `GROQ_JUDGE_MODEL` (default `openai/gpt-oss-20b`, which must differ from
  `GROQ_MODEL`) only when its Gemini judge models hit quota. It never judges an answer with the model that produced
  it; if none is left, the metric is marked "unjudged".
- **Safeguards:** Groq requests get the same rate limiter, the same PHI masking (`mask_phi`) and the same tracing and
  tool calling as Gemini requests.
- **Labelling:** every Groq call is labelled `provider=groq` in its spans, its own audit record and the tool/audit
  logs, and per case in `eval_report.json`. `eval_report.json` and `golden_signals.json` report the headline metrics
  for Gemini-only cases, and Groq-involved cases apart, with Groq call counts per step. `dashboard_data.csv` has a
  `provider` column.
- **Disclosure:** if any Groq call reaches the final evidence, it must be disclosed in the model card and the
  compliance doc (IMPROVEMENT_PLAN.md Phase 8c).
